# План разработки нового веб-интерфейса (эпик #117)

Документ для владельца и для исполнителей подзадач W-2…W-11. Описывает, как устроен новый
фронтенд в `web/`, в каком порядке переносятся экраны, что переиспользуется между сайтом,
кабинетом, админкой и мини-приложением и какие изменения нужны на сервере. Каркас (W-1, PR #129)
уже сделан по этому плану; дальше план обновляется в каждой подзадаче, если решения меняются.

Справочник по командам, сборке и правилам переноса: `docs/WEB-FRONTEND.md`. Здесь только план и
архитектурные решения.

## 1. Исходные данные

| Что | Объём | Где сейчас |
| --- | --- | --- |
| Сайт и кабинет | `app.js` ~2,4 тыс. строк, `telegram.js`, `invite.js`, `support.js` | `server/src/main/resources/web/` |
| Админка | 13 вкладок `ADMIN_TABS` (`app.js:1522`), часть в `control.js` | там же |
| Мини-приложение | `tg/app.js` ~800 строк, экраны `home`, `devices`, `pay`, `support`, `profile`, `connect`; `tg/open.js` | `web/tg/`, `http/MiniApp.kt` |
| API | ~110 маршрутов `/v1` в 11 файлах `http/*.kt`, ошибка `ErrorRes(ErrorBody(code, message))` | `server/.../http/` |
| Тексты | `S("en", "ru", "de")` | `shared/.../api/i18n/strings/` |

Нетипизированные ответы (`buildJsonObject`), которые стоит заменить на `@Serializable`-классы при
описании API: `/v1/auth/telegram/config` (`TelegramWeb.kt`), `/health` (`App.kt`), часть ответов
в `services/Control*.kt`, `Analytics.kt`, `Nodes.kt`. Решается в W-2, обратно совместимо (те же
поля и имена).

Итог W-2: `buildJsonObject` в ответах был только в `TelegramWeb.kt` (4 ответа) и `/health`; они
стали классами. В `Control*.kt` и `Analytics.kt` ответы уже были классами (`JsonObject` там только
в поле `details` журнала и во внутренних расчётах). `GET /v1/admin/nodes/{id}/balancer` отдаёт
фрагмент конфигурации Xray (`JsonObject`), это свободный JSON по своей природе; он описан в
OpenAPI как объект и не менялся.

## 2. Архитектура

### 2.1. Слои

```
приложения (entry)   site (сайт, кабинет, админка)        miniapp (Telegram)        tg-open
                              │                                  │                     │
экраны (features)    public · auth · account · referrals · invite · support ·          │
                     admin/* · status · analytics          miniapp/screens              │
                              │                                  │                     │
общие модули         ui-kit · layout · hooks · api (клиент + типы) · i18n · lib ───────┘
                              │
платформа            persistence: localStorage (site) | memory (miniapp)
```

Правило зависимостей: экран может импортировать общие модули и сам себя, но не другой экран.
Если кусок нужен двум экранам, он переезжает в общие модули (`components/` или `hooks/`).
Это проверяет ESLint (`no-restricted-imports` для `@/features/*/**` из чужой папки; общие модули
`api/`, `components/`, `hooks/`, `i18n/`, `lib/`, `store/` не импортируют экраны вовсе), правило
есть с W-3 (`web/eslint.config.js`), список папок `features/` берётся из файловой системы.

### 2.4. Слой API

- Один Axios-клиент (`api/client.ts`) для всех точек входа; токен берётся из стора, а не из
  `localStorage` напрямую, чтобы мини-приложение могло держать его в памяти.
- **Типы.** С W-2 все запросы идут через `api/typed.ts`: путь и метод из `schema.d.ts`
  определяют типы параметров, тела и ответа. Ручные интерфейсы (`Me` в `queries.ts`) удаляются.
- **Ключи запросов** через фабрику `api/keys.ts` (`keys.account.devices()`,
  `keys.admin.users(filter)`), чтобы инвалидация после мутаций была в одном месте.
- **Мутации** через хук `useApiMutation` (W-3): тост успеха/ошибки, инвалидация переданных
  ключей, `error.message` сервера в тосте.
- **Опрос.** `usePolling` поверх `refetchInterval`, останавливается на скрытой вкладке и при
  уходе со страницы (статус заказа W-4, статус серверов W-8, вход в приложение W-3).
- **Моки в тестах.** Общий хелпер `test/api.ts`: подменяет адаптер Axios, отвечает по пути и
  методу, типизирован теми же `schema.d.ts`. Не тянем MSW, если хватит адаптера.

**OpenAPI (W-2), рекомендуемый способ:** поддерживаемый файл `server/src/main/resources/openapi.yaml`
плюс два теста в `:server:test`: (1) множество маршрутов `/v1` из дерева Ktor совпадает с путями
спецификации; (2) ответы ключевых эндпоинтов тестового сервера проходят валидацию по схеме.
Генерация из кода Ktor не выбрана: в проекте нет аннотаций маршрутов, а генераторы схем из
`kotlinx.serialization` не покрывают `sealed`/`JsonObject`-ответы без ручной доработки; файл со
строгим тестом соответствия даёт тот же результат проще. Окончательное решение и обоснование
пишутся в `docs/WEB-FRONTEND.md` в W-2. Копия для фронтенда не нужна: `gen:api` читает тот же
файл из `server/src/main/resources/`.

**Решение W-2:** как рекомендовано, плюс третий тест: каждая схема компонента с `x-kotlin`
совпадает со схемой, построенной из `@Serializable`-класса (`OpenApiSchemas` в тестах), так что
модели и файл не расходятся; схемы для новых моделей печатает `OpenApiDumpTest`. Проверка ответов
строгая (незадокументированное поле — ошибка), валидатор свой, маленький, под подмножество JSON
Schema, которое использует файл (без новой зависимости). `/v1/openapi.json` отдаётся только
владельцу, всем остальным 404. Подробности в `docs/WEB-FRONTEND.md`, раздел «API description».

### 2.5. Состояние и сессия

- Zustand-стор `session` (есть): `token`, `role`, `site`, `lang`. В W-9 он становится фабрикой
  `createSessionStore(persistence)`: сайт передаёт адаптер `localStorage` (`lib/storage.ts`,
  те же ключи, что у `app.js`), мини-приложение передаёт адаптер в памяти.
- `lib/storage.ts`, запись cookie `lang` и всё остальное, что трогает web storage, импортируется
  только из `entries/site.tsx` и модулей сайта, а не из общих (`i18n/`, `api/`). Сейчас
  `i18n/index.ts` и `store/session.ts` импортируют `storage` напрямую; в W-9 зависимость
  разворачивается (передаётся при инициализации). Проверка: `MiniAppTest` ищет `localStorage`,
  `sessionStorage`, `document.cookie` в собранных файлах мини-приложения.
- Локальные настройки экранов (`monRange`, `anPeriod` и другие ключи `app.js`) читаются и
  пишутся через хук `usePersistedSearch(key, param)`: значение в адресе главнее сохранённого.

### 2.6. i18n

Остаётся как в W-1: ключ — английский текст, `t`/`tp` со строковыми литералами (так их находит
`I18nTest`), `/v1/i18n/<lang>`, английский без загрузки. Новые строки добавляются в
`shared/.../i18n/strings/` в том же PR, что и экран. Для мини-приложения сервер подставляет
язык аккаунта в шаблон; i18next инициализируется тем же модулем `i18n/` с языком из параметра,
детектор и cookie отключены.

### 2.7. Маршрутизация и точки входа

- Сайт: TanStack Router с hash history (есть), все маршруты и search-параметры объявлены в W-1.
  Экраны грузятся лениво (`lazyRouteComponent`) по разделам: публичный сайт, кабинет, админка,
  статус/аналитика, Swagger UI. Гость не скачивает код админки.
- Чанк `vendor` из W-1 (`codeSplitting.groups`) собирает все `node_modules`; в W-2 правило
  сужается, чтобы Swagger UI и `@hello-pangea/dnd` попадали в ленивые чанки, а не в общий.
- Мини-приложение: свой маленький роутер на hash (`#/pay`, `#/devices`, `startapp=`), без
  TanStack Router, если бандл с ним заметно больше; решается в W-9 по размеру.
- **База ассетов.** Сейчас `base: "/next/"`. В W-9 все точки входа собираются с одной базой
  `/ui/` (ассеты `/ui/assets/*` с хешами), а HTML отдаётся сервером на нужных адресах (`/next/`,
  `/tg/app-next`, позже `/` и `/tg/app`). Тогда переключение в W-10 не требует пересборки и
  одинаково работает с `WEB_UI=new` и `legacy`.

## 3. Стратегия миграции

1. Новый интерфейс живёт на превью (`/next/`, `/tg/app-next`), старый не меняется до W-10.
2. Каждая подзадача переносит экраны целиком, с паритетом по функциям, состояниям и адресам.
   Перенесённый экран заменяет заглушку в роутере; ссылки на ещё не перенесённые экраны ведут
   на старый сайт с пометкой (так было в W-6 для админки; с W-7 вся админка в новом интерфейсе).
3. Для паритета в каждом PR — таблица «функция старого экрана → где в новом» и скриншоты
   старого и нового на `:server:sim`.
4. W-10 включает новый интерфейс переменной `WEB_UI=new` (по умолчанию) с откатом на `legacy`
   без пересборки; старые файлы остаются в jar.
5. W-11 удаляет старые файлы только после подтверждения владельца.

## 6. Качество и проверки

- Каждый PR: `npm run typecheck`, `lint`, `test`, `build`; `./gradlew :server:test`; `web.yml` и
  `server.yml` зелёные.
- Vitest: логика (форматтеры, парсеры адресов, сборка тел запросов) — модульные тесты;
  экраны — Testing Library с моками API из `test/api.ts`.
- Браузерный тест (Playwright) появляется в W-9 для проверки CSP мини-приложения и в W-10 для
  адресов из писем и бота; запускается в `web.yml` против `:server:sim`.
- `I18nTest` уже сканирует `.ts`/`.tsx`.
- Доступность: у каждой формы подписи полей, фокус в диалогах, `aria-expanded` у меню,
  статусы текстом; проверка ESLint-плагином `jsx-a11y` добавляется в W-3.
- Размер: сборка печатает размеры чанков; ориентир для мини-приложения — до ~150 КБ gzip JS.
