# Лимит устройств на ключ: варианты

Документ для решения владельца. Код не менялся. Источники: ветка `claude/adoring-brown-s8fqex` (на 2 ноября 2026), ссылки на файлы и функции ниже.

## 1. Проверка фактов о текущем состоянии

| Утверждение из задачи | Результат | Где в коде |
|---|---|---|
| Лимит проверяется только при создании туннеля | Верно. `Tunnels.provisionFor` проверяет `activeTunnelCount(...) >= e.deviceLimit` и отвечает `DEVICE_LIMIT`; позже число устройств не пересматривается | `services/Tunnels.kt` (≈ стр. 266) |
| Считаются устройства `kind = 'device'` с туннелем, не удалённые | Верно | `Entitlements.activeTunnelCount` |
| Лимит из тарифа, по умолчанию 1 / 5 | Верно: `subscriptions.device_limit`, иначе `FREE_DEVICE_LIMIT`=1 и `PRO_DEVICE_LIMIT`=5. У владельца не меньше `OWNER_DEVICES` | `Entitlements.entitlement`, `Config.kt` (стр. 99–100) |
| Роуминг AmneziaWG штатный, один конфиг на нескольких устройствах перебивает друг друга | Верно по свойствам протокола (один peer, один endpoint). В коде панели этого нет, это поведение WireGuard | протокол |
| VLESS-ключ вне лимита, один UUID на пользователя | Верно: системное устройство `kind='vless_bonus'` (`KIND_VLESS_BONUS`), UUID не меняется | `services/VlessKeys.kt` |
| Жёсткого ограничения одновременных подключений для UUID нет | Верно. `VlessKeys.hasAccess` смотрит блокировку, конец бесплатного периода и месячный трафик | `VlessKeys.hasAccess` |
| Скорость бесплатного тарифа на VLESS не режется | Верно по описанию: у `SpeedLimits` для VLESS-нод лимита нет. Для AmneziaWG режет агент (`traffic.py`) | `services/Nodes.kt`, `resources/node/traffic.py` |
| Подписка `/k/{token}/vless` отдаётся любому, у кого есть ссылка; HWID не читается | Верно. Читаются только `User-Agent` и параметры `format`, `lang`; `x-hwid` нигде не используется (`git grep -i hwid` пуст) | `http/Web.kt` (≈ стр. 166), `VlessSubscription.kt` |
| Подписка открывается и по токенам AmneziaWG-ключей | Верно: `call.vless()` ищет пользователя по любому токену (`userByToken`) | `http/Web.kt` |
| Каждый вход создаёт новую строку `devices`; идентификатора устройства нет | Верно: `Auth.createSession` вставляет `devices`, `DeviceInfo` это имя и платформа | `services/Auth.kt`, `shared/.../Models.kt` (`DeviceInfo`) |
| Автоочистки устаревших устройств нет | Верно: удаление только вручную | поиск по `removed_at` |
| Сервисное устройство мини-приложения в лимит не входит | Верно: `createServiceSession`, без туннеля | `services/Auth.kt` (V25) |
| Агент раз в минуту шлёт endpoint и онлайн-IP; панель пишет в `client_ips` на 7 дней | Верно. `ClientIps.KEEP` = 7 суток, запись `ClientIps.record` из `Traffic.collect`; таблица V20 хранит только адрес, сервер и время | `services/ClientIps.kt`, V20, `agent.py` (`OnlineIps`) |
| «Уникальные IP за 24 часа» и флаг `sharing` при `> sharingThreshold` (5) | Верно: `count(DISTINCT ip)` за 24 часа по всем устройствам пользователя, флаг `ips > threshold`. Ничего не блокирует; адреса не группируются по подсетям | `services/Control.kt` (`ips24hCount`), `ControlModels.kt` (`DEFAULT_SHARING_THRESHOLD`) |

Уточнения и упущенное:

1. **VLESS-статистика зависит от настроек Xray на ноде.** Агент получает онлайн-IP только при `statsUserOnline: true` в политике (комментарий в `agent.py`, стр. 20); конфиг ноды в репозитории панели не генерируется целиком, поэтому включён ли параметр на каждой ноде, надо проверить на месте. Без него `client_ips` для VLESS пуст, и всё, что построено на IP, молчит.
2. **Один UUID размножается на все VLESS-ноды** (`VlessLocations`), значит один пользователь и один набор IP видны на нескольких нодах; `client_ips` ключуется по `(device_id, ip)`, поэтому счёт идёт по пользователю, а не по ноде. Это удобно для всех вариантов ниже.
3. **Устройства приложений Boop получают собственный UUID** с `kind='device'` и входят в лимит; обходят лимит только через подписку-ссылку (бонусный ключ).
4. **Слот занимает «мёртвое» устройство.** После переустановки приложения старая строка `devices` с туннелем остаётся, пока её не удалят вручную; для честного пользователя это самая частая причина ошибки `DEVICE_LIMIT`.
5. **Что вообще можно наказывать.** Для AmneziaWG число одновременных устройств само ограничено физикой (один peer = один endpoint). Реальная дыра одна: **подписка VLESS без лимита**. Все варианты ниже в основном про неё.

## 2. Варианты

### Вариант 1. Одновременные разные IP в коротком окне

**Как работает.** Источник тот же, что у `client_ips`, но смотрим не 24 часа, а окно (по умолчанию 5 минут) по полю `last_seen`. Адреса группируются: IPv4 по /24, IPv6 по /48 (так privacy-адреса и соседние адреса одного оператора это один «узел»). Если за окно виден порог разных групп (по умолчанию 3 для Pro) и ни у одной нет признаков «переезда» (старый адрес пропал в момент появления нового, то есть окна не пересекаются), срабатывает правило. Встраивается в панель: расширение `ClientIps.record`/`Traffic.collect` плюс таблица событий. Агент и клиенты не меняются.

**Точность.**
- Задержка: агент шлёт данные раз в минуту, Xray помнит IP, пока жива активная связь (`connIdle`, по умолчанию 300 с у Xray), поэтому «старый IP ещё онлайн» может держаться несколько минут после смены сети. Окно меньше 5 минут даёт ложные срабатывания при смене Wi-Fi на LTE.
- CGNAT и мобильные операторы: много разных людей за одним IP (занижаем число устройств) и один человек с разными IP из пула оператора в течение минут (завышаем; смягчается группировкой по /24 только частично, у операторов пулы шире).
- IPv6 privacy-адреса: ротация внутри /64, поэтому /48 надёжно сводит их в одну группу.
- Dual stack: одно устройство одновременно с IPv4 и IPv6 даёт две группы. Нужно считать по семейству отдельно и брать максимум, а не сумму.
- AmneziaWG: в `client_ips` попадает только endpoint последнего handshake, то есть там и так максимум один адрес на устройство; роуминг даёт смену, не добавление.

**UX.** Честный пользователь при смене сети ничего не заметит (порог по одновременным группам, не по общему числу). Шаг 1: уведомление (в боте и на сайте) «ключом пользуются с нескольких мест одновременно». Шаг 2: сброс ключа или подписки кнопкой «Перевыпустить ссылку» самим пользователем; временное отключение только по настройке.

**Совместимость.** Не меняет формат ссылок, работает со всеми клиентами (Happ, v2RayTun, Hiddify, Boop), с бонусным ключом вне лимита (#33), потому что лимит у него отдельный («одновременных мест», а не число устройств).

**Нагрузка и приватность.** Таблица уже есть; нужны индекс по `(device_id, last_seen)` и запрос раз в минуту на пользователей с VLESS. Новых данных нет, срок хранения 7 суток (можно сократить до 48 часов для сырых IP).

**Объём.** 2 этапа: наблюдение и уведомления (5–7 дней), жёсткие меры (3–4 дня). **Риски:** ложные срабатывания на CGNAT и семьях за одним роутером (это как раз разрешённый случай), зависимость от `statsUserOnline`.

### Вариант 2. Подписка с привязкой к устройству (HWID)

**Как работает.** Happ и v2RayTun отправляют заголовки устройства (`x-hwid`, `x-device-os`, `x-device-model`, `x-ver-os`; точный набор зависит от версии клиента и от флага «Запрашивать HWID» в профиле, это допущение, его надо проверить на реальных клиентах) при загрузке подписки. Сервер хранит HWID (в виде хеша) на пользователя; если уникальных HWID больше лимита тарифа, отдаёт пустой профиль или заглушку-ссылку «слишком много устройств». В кабинете, боте и мини-приложении появляется список HWID и «Сбросить устройства».

**Точность.** Не зависит от IP, CGNAT и роуминга, поэтому точнее варианта 1 для клиентов, которые HWID шлют. Клиенты без HWID (Hiddify, v2rayNG, клиенты sing-box/Clash) не различимы: для них нужно решение «пускать» (дыра остаётся) или «не пускать» (ломаем честных). HWID можно подделать, но это требует усилий.

**UX.** Честный пользователь добавляет подписку на свои телефон и ноутбук, в пределах лимита всё работает. Переустановка клиента может сменить HWID (зависит от клиента) и занять слот: нужна кнопка сброса и автоочистка (вариант 4). При превышении клиент показывает заглушку, которую мы задаём (имя профиля, поддержка).

**Совместимость.** Разосланные ссылки продолжают работать; первые загрузки просто начинают учитываться. Десктоп и мобильный Boop не затронуты (у них свой UUID). Бонусный ключ (#33) остаётся «вне лимита приложений», но получает отдельный «лимит HWID подписки».

**Нагрузка и приватность.** Одна запись на `(пользователь, hwid_hash)`, без истории IP. HWID считается идентификатором устройства, хранить только хеш с солью, указать в политике конфиденциальности.

**Объём.** 3 этапа: сбор HWID без блокировки (3–4 дня), список и сброс в кабинете, боте и мини-приложении (4–5 дней), ограничение (2 дня). **Риски:** разный набор заголовков у клиентов, часть клиентов не шлёт HWID, поведение клиентов на пустой подписке.

### Вариант 3. Отдельный VLESS UUID на каждое устройство подписки

**Как работает.** Вместо одного бонусного UUID каждое устройство подписки получает свой UUID (`kind='device'`), входит в обычный лимит, перевыпуск идёт по одному. Подписка по ссылке остаётся одна, но выдаёт UUID конкретного устройства; чтобы понять «какое устройство», нужен тот же HWID (то есть вариант 3 без варианта 2 не различает устройства по одной ссылке) либо отдельная ссылка на устройство (как сейчас AmneziaWG-ключи).

**Точность.** Идеальна, если ссылка выдана на устройство; плохо, если ссылку копируют (копия делит UUID).

**UX.** Хуже всех: пользователю нужно создавать ключ на каждое устройство, ломается идея «одна ссылка-подписка» (решение владельца в #88: пользователь получает только ссылку-подписку).

**Совместимость.** Ломает идею бонусного ключа (#33), требует миграции существующих UUID и пересылки ссылок; старые ссылки придётся оставить.

**Нагрузка.** Больше клиентов Xray на нодах (по UUID на устройство), больше записей в `tunnels`.

**Объём.** 5–8 дней, высокий риск. **Не рекомендуется** как основная мера.

### Вариант 4. Автоочистка устаревших устройств

**Как работает.** Периодическая задача: устройство с `kind='device'` без handshake и трафика N дней (по умолчанию 45) помечается к удалению: пользователю уведомление за 7 дней, затем `removed_at` и снятие туннеля. Опорные данные уже есть: `tunnels.last_ip`, `traffic_samples`, `devices.last_seen_at`.

**Точность.** Не про лимит как защиту, а про справедливость: освобождает слоты после переустановки. Риск: человек, неделю не пользовавшийся приложением в отпуске.

**UX.** Явное уведомление и возможность вернуть устройство (создать заново) снимают риск. Сервисные устройства (V25) и `vless_bonus` не трогать.

**Совместимость.** Все клиенты, потому что чистятся только строки панели. **Нагрузка:** лёгкая ночная задача. **Приватность:** новых данных нет.

**Объём.** 3–4 дня. **Риск:** низкий, при условии мягкого срока и уведомления.

## 3. Сравнение

| | 1. IP в окне | 2. HWID | 3. UUID на устройство | 4. Автоочистка |
|---|---|---|---|---|
| Закрывает дыру подписки | частично (по одновременности) | да, для клиентов с HWID | да, если ссылка на устройство | нет |
| Влияние смены сети | нет при окне 5 мин и группировке | нет | нет | нет |
| Ложные срабатывания | CGNAT, пулы операторов | смена HWID при переустановке | нет | долгий перерыв |
| Работает с любым клиентом | да (если `statsUserOnline`) | нет, только с HWID | да | да |
| Ломает ссылки и бонусный ключ #33 | нет | нет | да | нет |
| Новые персональные данные | нет (уже есть IP) | хеш HWID | нет | нет |
| Объём работ | 2 этапа, ~10 дней | 3 этапа, ~10 дней | ~7 дней | ~3 дня |
| Риск | средний | средний | высокий | низкий |

## 4. Рекомендация

Комбинация **4 + 1 (только наблюдение) + 2 (когда проверим клиентов)**, вариант 3 не делать.

Обоснование: честный пользователь страдает от слотов, занятых мёртвыми устройствами (вариант 4), и это самое дешёвое улучшение. Дыра подписки лучше всего закрывается HWID (точно и без вмешательства в сети), но не все клиенты его шлют, поэтому HWID вводим постепенно. IP-правило (вариант 1) остаётся страховкой для клиентов без HWID, но только как наблюдение и уведомление: на CGNAT оно будет ошибаться, и жёсткие меры по нему не стоит делать без накопленной статистики.

### Поэтапный план (каждый этап отдельная задача)

1. **Автоочистка устаревших устройств** (вариант 4): 45 дней без handshake и трафика, предупреждение за 7 дней в боте и на сайте, сервисные и `vless_bonus` не трогать. Показать в кабинете «последняя активность».
2. **Проверка `statsUserOnline` на всех VLESS-нодах** и отчёт в админке («ноды без онлайн-IP»), чтобы IP-статистика была достоверной. Параллельно ввести группировку подсетей (IPv4 /24, IPv6 /48) в «уникальных IP» админки, чтобы флаг `sharing` перестал реагировать на privacy-адреса.
3. **Наблюдение за одновременными группами IP** (вариант 1): окно 5 минут, порог 3 группы для Pro (1 для бесплатного, с учётом dual stack), только запись события и уведомление админу; пользователю пока ничего.
4. **Сбор HWID без блокировки** (вариант 2): хранить хеш, показать в кабинете список «устройства подписки» и кнопку «Сбросить»; собрать статистику, какие клиенты шлют HWID.
5. **Уведомления пользователю** о превышении (бот, мини-приложение, сайт) по данным этапов 3 и 4 с кнопкой «Перевыпустить ссылку».
6. **Жёсткие меры** по настройке (по умолчанию выключены): для клиентов с HWID пустой профиль при превышении лимита тарифа; для остальных временное отключение только при устойчивом превышении (3 раза подряд за сутки); перевыпуск UUID вручную через админку остаётся.

### Предлагаемые значения по умолчанию

| Параметр | Значение |
|---|---|
| Окно одновременности IP | 5 минут |
| Порог групп IP | Pro: число устройств тарифа + 1 (то есть 6), бесплатный: 3. Начинать с наблюдения |
| Группировка | IPv4 /24, IPv6 /48; IPv4 и IPv6 одного устройства считать отдельно и брать максимум |
| Срок автоочистки | 45 дней без активности, предупреждение за 7 дней |
| Хранение сырых IP | 7 суток (как сейчас), агрегаты событий 90 дней |
| Лимит HWID | число устройств тарифа (`deviceLimit`), бонусный ключ входит в этот счёт при подписке |
| Порядок включения | наблюдение, затем уведомления, затем жёсткие меры по отдельной настройке |

### Допущения

- Состав заголовков HWID у Happ, v2RayTun и других клиентов взят из общих сведений о клиентах и требует проверки на реальных версиях.
- Включён ли `statsUserOnline` на нодах, в репозитории проверить нельзя (конфиг ноды ставится вне панели).
- Пороги и сроки выбраны как стартовые значения, их стоит пересмотреть после этапа наблюдения.
